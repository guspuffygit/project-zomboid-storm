# What Storm Changes

Beyond loading mod jars, Storm rewrites a chunk of the game's bytecode at load
time to fix vanilla bugs, expose runtime tunables, dispatch events, and lift
hardcoded performance limits. Everything below is gated to the dedicated-server
JVM unless noted, and is always-on unless it points at a tunable flag in
[Server Configuration](server-configuration.md).

## Performance

- **Parallel server-LOS pipeline** — `ServerLOS` fans out across `1..16` worker threads (`Storm.ServerLosThreads` sandbox option); per-square LOS state, lighting arrays, and scratch vectors are made thread-safe and per-worker. Each worker owns a slot in the resized `LosUtil.cachedresults[]` so the vanilla per-square cache is reused instead of reallocated; concurrent `IsoRoom.onSee` dispatch is serialized through a single reentrant lock so room-discovery side effects stay deterministic.
- **Stride-based animal LOS** — `Storm.AnimalLOSTickInterval` distributes `IsoAnimal.updateLOS` across N ticks; `0` disables animal LOS entirely on servers where it isn't worth the cost. Side effect: `BaseAnimalBehavior.spotted()` — the sole award path for animal-sourced Tracking/Sneak/Nimble/Lightfoot XP — only runs from this scan, so stride N also divides that XP by N (`0` = none).
- **Stride-based virtual-animal simulation** — `Storm.VirtualAnimalTickInterval` runs the whole `AnimalZones.updateVirtualAnimals()` pass every Nth tick, raising `GameTime.perObjectMultiplier` to N on executing ticks so time-delta-driven movement and track expiry advance the skipped time in one step (vanilla's own bucket-scheduler compensation mechanism). `0` freezes virtual animals entirely.
- **Stride-based zombie ownership rescans** — `Storm.ZombieAuthTickInterval` strides the *unowned*-zombie path of `NetworkZombieManager.updateAuth()`: vanilla bypasses its 2 s gate whenever a zombie has no owner and re-runs the full O(connections × players) relevance scan every tick for every such zombie. Owned zombies keep the vanilla 2 s cadence untouched.
- **Stride-based inventory-item GC** — `Storm.InventoryItemSweepTickInterval` runs the idempotent orphaned-item sweep in `InventoryItemSystem.update()` every Nth tick instead of every tick.
- **O(1) `ServerLOS.findData(IsoPlayer)`** — vanilla scans an `ArrayList<PlayerData>` by reference per call, dominating `IsoPlayer.updateLOS()` on busy servers. Storm caches the lookup in an identity-keyed sidecar (`ServerLOSPlayerDataCache`, a lock-free `ConcurrentHashMap` so the per-call `get` takes no monitor).
- **Distance-culled player LOS scan** — vanilla `IsoPlayer.updateLOS()` walks *every* moving object in the loaded cell (thousands on a busy server) per player per tick, running a `ServerLOS.isCouldSee` lookup plus client-only bookkeeping (fade-in alpha targets, `musicZombies*` music-intensity fields, jump-scare state) that is not `bServer`-gated and that no server-side code reads. Storm skips objects outside the player's 96×96-square visibility cube before any cast/visibility work (outside it `isCouldSee` is always false and the vanilla body has zero server-visible effect), reads the visibility cube directly instead of doing a per-object map lookup, and strips the client-only writes. Zombie spotting (`TestZombieSpotPlayer` on both the lit and could-see branches), `TestIfSeen`, panic/boredom counters, and `lastSpotted` maintenance are vanilla-exact. ~18% of main-thread CPU at 79 players. Disable with the `Storm.PlayerLosFastPath` sandbox option; auto-reverts to vanilla permanently if the fast path ever throws.
- **Registry-backed in-use-entity sweep** — vanilla `UsingPlayerUpdateSystem.update()` null-checks *every* entity in the engine's iso-object bucket (123k+ on a busy server) each tick to find the handful whose `usingPlayer` is non-null (roughly the number of players with a crafting/entity UI open) and release them once the player leaves a ±10-tile box, changes Z level, or dies. Storm maintains an identity registry of exactly those entities — fed unconditionally from `GameEntity.setUsingPlayer` and the server branch of the `receiveUpdateUsingPlayer` entity packet (which bypasses the setter) — and sweeps only the registry, clearing through the real `setUsingPlayer(null)` so the vanilla client broadcast still fires. Release rules are vanilla-exact; entries whose entity left the engine (chunk unload) are evicted without touching world state. ~6% of main-thread CPU at 79 players. Disable with the `Storm.UsingPlayerSweepFastPath` sandbox option (safe to flip live — the registry stays complete while off); auto-reverts to vanilla permanently if the sweep ever throws.
- **Hoisted, reordered fluid-container pass** — vanilla `FluidContainerUpdateSystem.updateSimulation()` visits every registered FluidContainer entity on every 100ms simulation tick (plus uncapped catch-up ticks) and, per entity, re-reads `ClimateManager` precipitation state and the sandbox day length, and runs `getPrimaryFluid()` (a fluid-list scan) plus a `"Petrol"` string compare before the cheap rain guards; only the network sync is throttled, not the scan. Storm hoists the per-tick invariants (precipitation intensity/is-snow, day-length divisor, game-seconds-per-tick) out of the loop, evaluates the branches' shared cheap prefix (`canPlayerEmpty && rainCatcher > 0`) first so non-qualifying entities skip the fluid-list scan, and compares the petrol fluid by `FluidType` identity instead of by string (provably equivalent — modded fluids can never carry the builtin name). Rain fill, snow halving, and petrol evaporation are vanilla-exact, in vanilla order; the `objectSyncLimiter`-throttled per-branch syncs are coalesced into one full-state send after the last mutation (vanilla sends twice back to back when a container hits both branches in the same sync window — each packet snapshots current full state, so the single deferred send delivers the identical final client state). ~6% inclusive of main-thread CPU at 79 players. Disable with the `Storm.FluidContainerUpdateFastPath` sandbox option; auto-reverts to vanilla permanently if the fast path ever throws.
- **Relevancy-gated object sync broadcasts** — the server paths of `IsoObject.syncIsoObject` (and the `IsoWorldInventoryObject`, `IsoBarricade`, and `IsoLightSwitch` overrides) send every SyncIsoObject full-state packet — rain barrels, generators, hutches (whose per-egg inventory serialization makes multi-KB payloads), dropped items, barricades, light switches — to **every** connection. A client without the object's square loaded discards the packet on arrival (`GameClient.receiveSyncIsoObject` finds no square), so out-of-range sends are pure waste: 972 KB/s at 103 players on a production server, the #2 outbound packet type, dominated by the 1 s rain-barrel sync window. Storm gates each send with vanilla's own `IsoDoor.syncIsoObject` precedent — `isFullyConnected() && isRelevantTo(x, y)` — reproducing everything else (error guards and their console output, receive-side field application, source-connection exclusion, `IsoLightSwitch`'s custom inline payload with its missing-index fallback, `flagForHotSave`) expression for expression; `syncIsoObjectSend` still dispatches virtually so subclass payloads are vanilla-built. State on a client that was out of range while an object changed self-heals the way vanilla already relies on for every un-synced mutation: full object state rides in the chunk payload when the chunk streams back in. The base-method patch covers every subclass without its own override; `IsoStove` and `IsoCurtain` keep their vanilla loops (their receive branches touch private state, and both are low-volume event-driven senders). Suppressing *later* duplicate syncs generically (coalescing windows) was considered and rejected: each send serializes current state, so deferral would delay real state and a suppression window would need per-object-per-connection bookkeeping — the relevancy gate plus the fluid-pass coalesce above capture the win without either. Always on; auto-reverts to vanilla broadcast permanently if the gated path ever throws.
- **Relevancy-gated GameEntity broadcasts** — the server broadcast branch of `GameEntityNetwork.sendPacketData` hands every GameEntity packet — craft-progress ticks (`CraftLogicSync`, a full craft-state re-serialization including inventory items, re-sent every 1000 ms per running station on a timer with no dirty check), component dumps (`SyncGameEntity`), using-player changes — to `INetworkPacket.sendToAll`, whose only filter is `isFullyConnected()`. A client without the entity's chunk loaded has no registered entity to apply the packet to, so out-of-range sends are pure waste: ~1.06 MB/s at ~1080 pkts/s at 103 players on a production server, the #1 outbound packet count. Storm replaces the broadcast loop with vanilla's own object-sync precedent (`INetworkPacket.sendToRelative`) — `isFullyConnected() && isRelevantTo(x, y)` — applied only to `GameEntityType.IsoObject` entities with a square (placed world objects, the relevancy anchor); inventory-item, vehicle-part, moving-object, and meta-entity packets keep the vanilla broadcast. Exclusion semantics, validation-warn bypasses (vanilla prints its own output), and the pooled `EntityPacketData` release are reproduced exactly. State on a client that was out of range while an entity changed self-heals the way vanilla already relies on: current entity state rides in the chunk payload on stream-in, and the next 1 s `CraftLogicSync` arrives as soon as the client becomes relevant. Always on; auto-reverts to vanilla broadcast permanently if the gated path ever throws.
- **Memoized ECS component-class lookup** — the static `ECSComponent.getECSClass(Class)` walks the superclass chain up to `ECSComponent` on every call, and it sits under every `getECSComponent`/`hasECSComponent`/`removeECSComponent` (per character per tick via `getStateMachine()` and AI lookups — millions of calls/second, ~2.9% self time at 79 players). The walk is a pure function of the class, so Storm memoizes it in a `ClassValue` (JVM-optimized, weakly referenced, classloader-safe) whose compute encodes the identical loop — results match vanilla for every input, including `null` and `ECSComponent.class` (both routed to the vanilla body, which returns `null`). Disable with the `Storm.EcsClassCache` sandbox option (always safe to flip live); auto-reverts to vanilla permanently if a lookup ever throws.
- **Budgeted cell unloads** — vanilla `ServerMap.postupdate()` destructively unloads *every* loaded cell that fails the relevance check in a single tick; each `ServerCell.Unload()` walks 64 chunks → `IsoChunk.removeFromWorld()` → per-entity engine unregistration, so a burst of stale cells (players logging off or moving together) turns into one multi-hundred-ms tick spike (~11% of the main thread during a burst window at 79 players, near-zero steady-state). Storm replaces the loop with a faithful reimplementation that unloads at most `Storm.CellUnloadBudgetPerTick` cells per tick (default 2); stale cells beyond the budget stay in `loadedCells` and are re-evaluated next tick, so a cell that becomes relevant again is naturally kept and a stale one unloads a few ticks later. Every side effect of the cells it does unload is vanilla-exact and in vanilla order: the cancel-loading bookkeeping for in-flight cells, `cell.update()` for relevant cells, the `ServerLOS.instance.suspend()`-before-first-unload / resume-in-finally bracket, the `catch (Exception)` swallow, and the `NetworkZombiePacker.postupdate()` / `chunkLoader.updateSaved()` tail. Deferral is safe: `loadedCells` is bounded by player relevance, `SaveAll`/`QueuedSaveAll` save deferred cells like any other loaded cell, and `ServerCell.Unload` queues its chunk save jobs whenever the cell eventually unloads. Set the option to `0` to restore vanilla; auto-reverts to vanilla permanently if the budgeted body ever throws. Composes with cell warming (`-Dstorm.cells.keepWarm`): when warming is on, the warm pass owns `postupdate` and the budget defers to it.
- **O(1) entity unregistration** — `EngineEntityManager.removeEntityInternal` removes each departing entity from the engine's global entity array via `Array.removeValue`, a linear identity scan of ~123k live entities (3.1% main-thread self time during cell-unload bursts — the dominant per-entity cost under `IsoChunk.removeFromWorld`). The array is unordered, so vanilla's removal is already swap-with-last O(1) — the cost is purely the index search. The same removal also runs `EntityBucketManager.updateBucketMembership`, which re-scans every `EntityBucket`'s own entity array linearly (the remaining ~2% of main-thread time after the global index shipped). Storm maintains an identity index (entity → position) per tracked array — the global array plus every bucket's, each carrying its index in a field the load-time patch injects into `Array` itself — fed from the arrays' only mutation sites (the single-arg `add` and `removeValue`; the fields are private and never leaked mutably; world reload constructs fresh arrays that constructor hooks on `EngineEntityManager` and `EntityBucket` re-track) and removes by index lookup + swap fixup instead of scanning. Before using an index it verifies the slot actually holds that entity; any mismatch falls back to the vanilla scan and latches the fast path off permanently, so a wrong removal is impossible. Disable with the `Storm.EntityRemoveFastPath` sandbox option (safe to flip live; re-enabling rebuilds the index once).
- **Chunk-windowed zombie-sight vehicle occlusion** — vanilla `IsoZombie.isVehicleBetween` iterates *every* vehicle in the loaded cell per zombie sight test, inverting each vehicle's world transform twice, even when the result is provably unused (spot `chance` already zero, or the target sits in a vehicle). Storm skips the scan entirely in those cases and otherwise tests only vehicles registered in the chunks overlapping the ≤20-tile sight segment, with a cheap center-vs-segment reject before the vanilla-exact OBB intersection. ~14% of main-thread CPU on a vehicle-heavy server. Disable with the `Storm.ZombieSightVehicleFastPath` sandbox option.
- **Configurable server tick rate** — `Storm.ServerFps` lifts the hardcoded 10 TPS cap and sets the main-loop tick gate, `PerformanceSettings.getLockFPS()` on the server, and the `IsoPhysicsObject.update()` FPS scalar from a single value.
- **Tick-rate-aware random rolls** — `RandInterface.AdjustForFramerate` hardcodes a 10-TPS scalar on the server, so at `Storm.ServerFps > 10` every per-tick random event (fire spread, wound infection, footstep noise, drunk stumbles, ambients, vehicle engine auto-stall since 42.20.0) would fire `fps/10`× too often per real second. Storm rescales by the live lock fps (`chance * fps / 30`); bit-identical to vanilla at 10 TPS.
- **Non-boxing `Stats.get(CharacterStat)`** — eliminates per-frame `Float` autoboxing on the hottest character-stat accessor.
- **Skip server-side electricity scan** — `IsoGenerator.update` stops iterating chunk tiles on the server (the result is only used by the client UI); chunk-position bookkeeping is used instead. The full scan still re-runs once per in-game hour per activated generator so `totalPowerUsing` (the fuel-drain rate) tracks load changes between activations — e.g. 42.20.0's light switches, which register as generator loads and toggle at dusk/dawn.
- **Pool in-use set compaction** — `zombie.util.Pool.PoolStacks` tracks every checked-out object in a Trove `THashSet` whose constructor calls `setAutoCompactionFactor(0.0F)`. That disables `THash.removeAt`'s tombstone GC, so every release leaves a REMOVED slot that is never reclaimed; `TObjectHash.insertKeyRehash` only terminates its probe walk at a FREE slot (tombstones are recorded as `firstRemoved` but do not stop the walk), making the average insert probe `capacity / (_free + 1)`; and an insert that reuses a tombstone returns without setting `consumeFreeSlot`, so `_free` drains only on the ever-rarer inserts that meet no tombstone. The `_free == 0` emergency rehash is therefore reachable only asymptotically — the table spends hours at its worst before self-healing, then repeats. Measured on a production server at 14.5 h uptime: `Pool<AnimatorsBoneTransform>` at `capacity=823117`, `_free=7`, 510k tombstones — ~102,889 reference comparisons per `alloc`, and 41.9% of the server main thread when sampled earlier at `_free=20`. The set is pure bookkeeping (it backs one release-time assertion and the debug `PoolCounter` totals); the actual free list is the sibling `ArrayList`, which was always O(1). At the start of every world save Storm measures every pool's main-thread in-use set — two field reads per pool under the lock the owning thread already holds — and compacts any table whose average probe exceeds 64 at a capacity of at least 1024. Compaction is a plain rehash-to-fit: `_size` is preserved, `computeMaxSize` resets `_free`, and every pooled type uses identity hashing, so no element can move or be lost.

  The sweep is driven from a Byte Buddy advice on `ServerMap.QueuedSaveAll(false)`, reached from `preupdate()` on the main loop — the only place the server is already committed to blocking for hundreds of milliseconds, so the ~9 ms rehash folds into a hitch the players were getting anyway. Compaction must run on the thread that owns the `ThreadLocal` stacks and cannot interleave with `RagdollController.checkForActiveRagdoll`, the one server-side caller that iterates the in-use set without the lock; the save runs on the main loop, the same thread every pooled type is allocated from, so the invariant holds. Clients are **not** paused when the save window opens — `ServerMap.checkClientPause()` broadcasts `StartPause` only after the save has already run 600 ms — but what matters here is that the main thread is already blocked. `QueuedSaveAll(true)`, the shutdown path, runs on the shutdown-hook thread and is skipped: the stacks are `ThreadLocal` and compacting there would rehash the wrong thread's table. A server with `SaveWorldEveryMinutes=0` never saves and so is never compacted; degeneration takes hours to form and any ordinary save interval resolves it long before it becomes a problem. Server-only; any throwable latches the sweep off for the session.
- **Orphaned animation player reclaim** — `IsoGameCharacter.animPlayer` is pool-allocated lazily by `getAnimationPlayer()` and returned only by `releaseAnimationPlayer()`, which no `removeFromWorld()` override calls. Vanilla leans on deferred-removal lists instead, and only one closes the loop: `VirtualZombieManager.update()` hands a zombie to the reuse queue 5 s after removal and `IsoZombie.resetForReuse()` releases the player, but `AnimalPopulationManager.update()` expires its entry after the same 5 s while only stopping the emitter, and `IsoPlayer.RecentlyRemoved` is drained by `IsoPlayer.UpdateRemovedEmitters()`, which `IsoWorld` calls under `if (!GameServer.server)` — so on a dedicated server that list is never drained at all. A fourth group never reaches a removal path at all: dead animals and zombies observed sitting out of the world with no square and `removedFromWorldMs` still `0`. Every one of these strands its animation player permanently, and a removed player strands itself as well. They are not garbage: `Pool.PoolStacks.inUse` holds a strong reference, pinning the character and, through `AnimationPlayer.boneTransforms`, its `AnimatorsBoneTransform` objects at roughly 34:1 — which is what grows the table the compaction sweep above has to repair. Measured on a production server at 20 min uptime with 34 players: 2055 animation players in use, 2036 held by characters actually in the world, three by `IsoPlayer`s already gone (oldest 12.8 min past removal) and sixteen by dead animals and zombies carrying no removal stamp. Storm sweeps the pool's in-use set across every thread (the set is `ThreadLocal`-confined, so it is enumerated through `PoolCounter.poolStacks` rather than read from the sweeping thread) and calls `releaseAnimationPlayer()` on any holder absent from both `IsoCell.objectList` and `addList` that has been continuously out of the world for `-Dstorm.animplayer.sweep.graceMs` (default 60 s, an order of magnitude past vanilla's 5 s windows), then drops the matching entries from `IsoPlayer.RecentlyRemoved`. Age comes from `removedFromWorldMs` when vanilla set it and otherwise from the first sweep that saw the character absent, so the unstamped group ages too; a character that returns to the cell loses its entry and starts the grace period over. The release goes through the character rather than the pool because `getAnimationPlayer()` only re-allocates when the field is `null` — releasing directly would leave the character pointing at an object the pool had already re-issued. Because the decision reads observed state rather than assuming a call site is terminal, it cannot fire for a character in the world, and an animal that is virtualized and re-realized inside the window is never touched. Delivered as an `EveryOneMinuteEvent` handler rate-limited by `-Dstorm.animplayer.sweep.intervalMs` (default 30 s), so it runs on the main thread — the only thread that mutates the cell membership it reads and the list it drains. Server-only; any throwable latches the sweep off for the session. Disable with `-Dstorm.animplayer.sweep=false`.

## Behavioral overrides

- **Packet rate limit disabled on the server** — `PacketsCache.isLimitExceeded(...)` is short-circuited, so the vanilla `ServerOptions.maxPacketsPerSecond` cap does not apply to inbound or outbound traffic.
- **Net-data drain cap** — `GameServer.mainLoopDealWithNetData` (HIGH + player-update + vehicle inbound drain) gets a per-outer-loop-spin wall-clock cap from `Storm.NetDataCapMs` (default 90 ms; `0` disables). When the cap fires, subsequent packets in the same spin are short-circuited (dropped — RakNet already ACKed them on receipt, so nothing is retransmitted regardless of declared reliability; periodic state is regenerated next tick, one-shot packets are lost — the same tradeoff as vanilla's 70 ms vehicle-queue drop) and the next spin starts fresh. Protects world-tick scheduling during reconnect storms; drops counted by `pz_netdata_dropped_total` (also published under the deprecated misnomer `pz_netdata_deferred_total` for dashboard compatibility). **Exemptions:** `VehicleRequest` packets are processed even while the cap is engaged (counted by `pz_netdata_vehicle_request_exempt_total`) — they are the only inbound path that produces a `VehicleFullUpdate` for a client that lost a vehicle, and dropping them left cars invisible for the whole load window on high-population servers. Volume is bounded to one batched packet per client per 100 ms. Packets from connections that have not completed the join handshake (`UdpConnection.isFullyConnected()` false) are also exempt (counted by `pz_netdata_prejoin_exempt_total{type=...}`, plus a throttled WARN) — the login funnel (Login, LoginQueueRequest, Checksum, LoginQueueDone, PlayerConnect) is one-shot and never retried by the vanilla client, so a single drop silently strands the join until the stalled-connection reaper kills the client. Observed live: a cold-start `LoginPacket.processServer` taking 474 ms blew the budget and dropped the `LoginQueueRequest` queued in the same burst. Finally, a static allowlist of one-shot unretried types is always processed (counted by `pz_netdata_type_exempt_total{type=...}`): `CreatePlayer`/`ConnectCoop` (the respawn path has no timeout — a drop wedges the client on the respawn screen forever, and the stalled-connection reaper never candidates fully-connected connections), `TimeSync` (sent once right after PlayerConnect; a drop leaves `getServerTime()` at 0 all session, breaking vehicle interpolation, hit reactions, and the item-transaction sweep clock), `NetTimedAction`/`BuildAction`/`FishingAction` (a dropped request freezes the player's timed-action queue for ≥ 30 min), and `RequestData` (world download sends each request/ACK once and spins waiting; currently pre-join anyway — listed as insurance against a PZ update reordering the join sequence). All are join/respawn/action-rate-bounded.
- **Per-peer send-buffer watchdog** — `Storm.PeerSendBufferKickMb` (default 20 MB) and `Storm.PeerSendBufferKickHoldTicks` (default 50 ticks ≈ 5 s @ 10 TPS) auto-disconnect any peer whose HIGH-priority outbound RakNet queue stays above the threshold for the hold window. Bounds server-side memory growth caused by a peer on a saturated/lossy uplink that can't drain the broadcast firehose PZ queues for every `fullyConnected` peer. Setting MB to `0` disables the kick while leaving the per-peer telemetry gauges live (`storm_peer_*`). Auto-kicks are counted by `storm_peer_kicked_send_buffer_total`; the disconnect reason is `storm-send-buffer-overflow`.
- **Zombie culling** — vanilla-owned. Set `ZombieConfig.ZombiesCountBeforeDelete` directly; Storm publishes the live value as `storm_zombie_cull_threshold`. See [server-configuration.md](server-configuration.md#zombie-culling-is-a-vanilla-option).
- **UUID-based item transfers** — `StormTransferHandler` replaces vanilla's per-player byte-ID `Transaction` system for player ↔ player / bag / world / vehicle-part transfers; floor drops and dead-body containers still use vanilla. Eliminates ID-wraparound collisions and the "vacuous truth on ID 0" reject bug. Driven from `client/StormTransferFix.lua` over `sendClientCommand("StormTransfer", ...)`.
- **Faster natural-water collection** — `StormFastFillNaturalWater` overrides `ISTakeWaterAction:getDuration()` so filling from rivers, lakes, and other natural sources finishes in 100 ticks instead of vanilla's much-longer pull (taps and rain barrels are unaffected).
- **Mod command dispatch** — `CommandBase.findCommandCls` and `getSubClasses` consult `StormCommandRegistry`, so mod commands resolve in chat and show up in `/help` alongside vanilla ones.
- **Custom child-JVM bootstrap** — `CoopMaster` is rewritten to launch hosted servers through Storm's agent instead of a bare `ProcessBuilder`, so in-game-hosted servers also load Storm.
- **Protected uncaught exception handler** — the handler Storm installs at startup cannot be replaced by mods or vanilla code that calls `Thread.setDefaultUncaughtExceptionHandler`, so crashes always route through Storm's log writer.
- **Death triggers split by type** — vanilla fires `OnCharacterDeath` for every death (players, zombies, animals — note `IsoAnimal` extends `IsoPlayer`, so an `instanceof IsoPlayer` filter doesn't exclude livestock), forcing every subscriber to repeat the type tests. On the server, `OnDeathTriggerPatch` rewrites `OnDeath()` (in `IsoGameCharacter` and the `IsoAnimal` override) to fire a new `OnDeath` trigger for every death, then a per-type trigger: `OnAnimalDeath` for animals, `OnZombieDeath` for zombies (distinct from vanilla's earlier-firing `OnZombieDead`), and `OnPlayerDeath` for players (vanilla fires that name on the client for the local player only; Storm extends it to every player death on the server). Players — and any future character subtype, as the catch-all — additionally fire the deprecated `OnCharacterDeath` for backwards compatibility. Java subscribers use `OnDeathEvent` / `OnAnimalDeathEvent` / `OnZombieDeathEvent` / `OnPlayerDeathEvent`; Lua uses the same names on `Events.*`. Server-only: the client JVM stays on vanilla bytecode, where every death still arrives on `OnCharacterDeath` and the new triggers never fire.
- **Event hooks** — packet receipt (`OnPacketReceived`), ban actions (`onBanUser` / `onBanIp` / `onBanSteamID`), chat messages, Lua VM init, world-map render, item-transfer completion, and ~190 Lua event bridges become subscribable from Java via `@SubscribeEvent`. See [Mod Author Guide](mod-author-guide.md).
- **Pre-login workshop query** — `ServerQueryPatch` adds a Storm-only packet pair (ids `0x7A17` / `0x7A18`, payload magic `"STMQ"`) answered at the top of `GameServer.addIncoming`, ahead of vanilla's login gate. It reports the server's workshop item ids, mod ids, Storm/game versions, name, and player counts to the [Storm Launcher](launcher.md#workshop-query-over-udp) so players can pre-update mods over the port they already connect to, with no HTTP port exposed. The querying peer never logs in and never takes a slot; replies are capped per connection and the handler fails soft. Non-Storm servers simply never answer.
- **Custom role positions pinned to `user`** — vanilla `Roles.updatePositions()` renumbers every custom (non-read-only) role `0..N` on each `Roles.save()`, placing them strictly below the built-in `user` role (2000). `PlayerPacket`'s relay treats any peer whose role position is strictly greater than the sender's as a higher-ranked observer and relays that sender map-wide via `PlayerUpdateReliable`, which feeds the `PlayerDataRequest` refusal loop (~5.8k pkt/s at peak on a 130-player server). `RolePositionPin` sets every custom role's position equal to `user`'s on `OnServerStarted` (after the DB load, before any player joins) and again after every `RolesEditPacket` (post-vanilla renumber; persists the corrected positions and re-sends the role table to clients). Side effect: the `>=` position checks in kick/ban/`setaccesslevel` now treat all custom roles and `user` as equal rank. Server-only, fails soft.
- **Storm and Storm mod updates restart the server**: if Storm or a Storm mod updates, the server quits so the new files load on the next start.

## Bug fixes shipped with Storm

Each line below is a vanilla bug Storm patches out, all default-on.

- **Cross-player action cancel** — `ActionManager.removeFromQueue` filters by byte action id alone in vanilla, so cancelling your own action also yanks every other player's queued action with the same id. Patched to filter by `(byteId, onlineId)`.
- **Cross-player transaction cancel** — same shape on `ItemTransactionPacket`: one player's cancel rejects every other player's pending transfers in vanilla. Patched to filter by `(byteId, onlineId)`.
- **Stale transaction cascade** — `TransactionManager`'s consistency check rejects every new transfer after a container unloads mid-flight in vanilla; the patch sweeps stale transactions before the check.
- **Transaction byte-ID wraparound + ID-0 vacuous truth** — the vanilla `Transaction` allocator hands out 8-bit ids that wrap and collide across players, and `createItemTransaction` returns `0` on failure, which then matches every "no transaction" check downstream. Replaced by `StormTransferHandler`'s UUID-keyed protocol for player / bag / world / vehicle-part transfers.
- **Zombie id collisions ("zombie mitosis")** — vanilla's free-running 16-bit allocator wraps and reuses live ids on high-population servers; replaced with hash-probed allocation in `IsoObjectIDAllocate`.
- **Zombie map invariant** — `IsoZombie.update` re-establishes "`onlineId != -1` ⇒ in `ServerMap.zombieMap`" every tick, so chunk-load zombies stay in authoritative state.
- **Livestock and wildlife go invisible until a server restart** — animals are registered into `AnimalInstanceManager.AnimalMap` in exactly one place, `IsoAnimal.init(AnimalBreed)` (creation and load-from-disk), but the real ⇄ virtual round trip is asymmetric around it. When an animal in `AnimalZoneState` wanders out of the loaded area, `IsoMovingObject.postUpdate` calls `AnimalPopulationManager.virtualizeAnimal`, which parks the *live instance* inside a `VirtualAnimal` and then calls `IsoAnimal.delete()` — unregistering it and broadcasting a delete to clients. When the chunk comes back, `AnimalManagerMain.fromWorker` re-realizes that same instance (`addToWorld()` + `IsoCell.getObjectList().add`) and never calls `AnimalInstanceManager.add`. `AnimalSynchronizationManager.sendUpdateToClient` resolves every pending id through `AnimalInstanceManager.get(onlineID)` and silently skips a `null`, so the animal is never sent to any client again for the rest of its life: it ticks, eats, breeds, blocks movement and shows up in `/list animals`, but no player can see it. The peer virtualization path is fine — `removeChunkFromWorld` uses `unloaded()` + `n_addAnimal(...)` with no `delete()`, and `IsoChunk` line 3226 unregisters only `if (GameClient.client)` — so only the wander-out path loses the entry. A restart masks the bug because `AnimalCell.load` → `VirtualAnimal.load` → `IsoAnimal.load` → `init()` re-registers the whole save, which is why players report animals coming back after a restart and vanishing again hours later. Measured on a live 42.20.3 server ~8 h after restart: 180 of 365 animals in the cell object list were unreachable through `AnimalMap`, every one of them carrying a non-zero `removedFromWorldMs`. `IsoAnimalRegistryFixPatch` attaches an exit advice to `IsoAnimal.update()` that re-establishes "`AnimalInstanceManager.get(getOnlineID()) == this`" every tick — same shape as the zombie map invariant above. An empty slot is re-claimed under the animal's existing id so clients that still know it keep continuity; a slot held by someone else (or an animal still carrying the `IsoPlayer.onlineId` default of `1`) gets a fresh id from the probe-for-free `allocateID()`. Healing is immediate rather than deferred to the next realization, so a world already in the broken state repairs itself within a tick. Counters: `storm_animal_map_orphan_fixes_total`, `storm_animal_map_collision_total`. Server-only.
- **Pop-cell save append accumulation** — `IsoChunk.removeFromWorld` calls `ZombiePopulationManager.requestSaveCell` on every chunk unload, and the native `n_saveCell` appends each snapshot to `Saves/.../zpop/zpop_X_Y.bin` rather than overwriting it, so the same live zombie's 12-byte record accumulates dozens of copies in the same file as a player roams a pop cell. On the next reload, native emits every accumulated copy and N visually identical zombies spawn at the same square with sequential online ids — the cluster-of-clones behavior players colloquially call "zombie mitosis," distinct from the id-collision bug above. Storm short-circuits `requestSaveCell` on the dedicated server (`RequestSaveCellSuppressPatch`); the global autosave path that writes `zpop_virtual.bin` is independent and persists live zombies on the normal cadence. **Caveat:** the patch prevents new dupes from being written, but existing `zpop_X_Y.bin` files on disk still hold accumulated copies and will keep spawning clones on cell load until the on-disk files are cleaned (delete to regenerate from descriptors, or dedup in place).
- **Mid-handshake relevance leak (zombies at world origin)** — `UdpConnection`'s constructor initializes `releventPos[0] = new Vector3()` with default `relevantRange = 0`. Until the client's first `PlayerPacket` fires (typically 30+ s into the world-download handshake), the connection's stored "player position" is exactly `(0,0,0)`. `ServerMap.outsidePlayerInfluence` iterates every connection without filtering on `isFullyConnected()`, so the four ServerCells whose corners touch world `(0,0)` — `(0,0)`, `(0,-1)`, `(-1,0)`, `(-1,-1)` — claim relevance during every handshake. Cell `(-1,-1)` is suppressed by an unrelated guard; the other three stay in `loadedCells`, `LoadedAreas(serverCells=true)` reports them to the native pop manager, and virtual zombies materialize into the empty origin terrain. Storm short-circuits the four `UdpConnection` relevance methods (`isRelevantTo`, `RelevantToPlayerIndex`, `RelevantTo`, `getRelevantAndDistance`) to return "not relevant" whenever `isFullyConnected()` is false (`UdpConnectionRelevancePatch`), so handshaking connections do not force origin cells loaded. **Caveat:** the patch prevents further accumulation, but zombies already materialized at origin remain — clean them up server-side with `cell:getZombieList()` + `:removeFromWorld()`/`:removeFromSquare()` filtered by radius.
- **Everyone stuck on "Getting Server Info..." once a server gets busy** — two independent vanilla defects compound into a server that silently stops accepting anyone. First, `GameServer.startServer` builds the RakNet peer with a **hardcoded** cap of 101 incoming connections (`new UdpEngine(defaultPort, udpPort, 101, serverPassword, true)`) and never consults `MaxPlayers`; since `ServerOptions.getMaxPlayers()` is itself capped at 100, a full-size server has *one* spare socket for its entire login pipeline. Second, the only reap path for stalled logins — inside `GameServer.main`'s `updateDBCount > 150` block — is gated on `connection.getUserName() == null`, so a client that sent its username and then died anywhere later in the handshake (workshop init, mod check, chunk download, character creation) holds its slot **forever**; nothing else removes it, and RakNet's keepalive does not help because the peer stays responsive at the RakNet layer while the game-level handshake is dead. Leaked slots accumulate until the peer is full, at which point RakNet answers every new joiner with `ID_NO_FREE_INCOMING_CONNECTIONS` — a packet the vanilla client never handles (it exists only as a constant in `RakNetPeerInterface`), so there is no `OnConnectFailed`, no state change, and no timeout: `ConnectToServer.lua` keeps the last ZNet state label it was given and the player sits on **"Getting Server Info..."** indefinitely. Observed on a 100-slot production server: 12 unreapable connections aged 16–25 minutes pinning 99 of 101 slots, and every join attempt hanging. Storm fixes both halves server-side. `GameServerStalledConnectionReapPatch` sweeps from `launchCommandHandler` (called once per tick on the server main thread, so `disconnect` never runs off-thread; the sweep throttles itself to `-Dstorm.reapSweepIntervalMs`, default 30 s) and drops any connection that has not reached `isFullyConnected()` within `-Dstorm.reapStalledConnectionMs` (default 10 minutes) of a sweep first seeing it. The budget is wall-clock, not idle time: `setFullyConnected()` only fires when the character actually spawns (`receivePlayerConnect`), so this kicks both dead handshakes *and* players parked on the pre-spawn "Click Start" screen, even if their client keeps chattering at the packet level. Fully-connected players are never candidates; connections awaiting co-op approval, sitting in the login queue, or pending Google-auth get their clock re-stamped every sweep, so their budget only starts once the exempt state ends (note vanilla's `loginQueueConnectTimeout` merely *forgets* a timed-out `currentLoginQueue` without disconnecting it — the reaper is what actually frees that slot). Connections actively downloading chunks are likewise re-stamped: `PlayerDownloadServerChunkActivityPatch` marks every chunk-request wave as it arrives at `PlayerDownloadServer.getClientChunkRequest`, so a client legitimately spending longer than the budget streaming the world over a slow link is never kicked mid-load. That exemption matters beyond wasted progress — vanilla's loading thread races `GameClient.client` between `IsoWorld.init` and `IsoCell.LoadPlayer`, so *any* disconnect during the loading screen crashes an unmodified client with `NullPointerException: ... PlayerDB.getInstance() is null` instead of a "connection lost" message. Campers cannot hide behind it: a client that stops requesting chunks (spawn-screen idler, dead peer) goes quiet on this signal even while RakNet keepalive stays chatty, and its budget runs down normally. `GameServerConnectionCapPatch` substitutes the hardcoded literal with `clamp(max(vanilla, MaxPlayers + storm.raknet.connectionHeadroom), .., min(256, GameServer.SlotToConnection.length))` (default headroom 64). 42.20.3 absorbed most of this fix — the vanilla literal is now 255 rather than 101, and `SlotToConnection` shrank from 512 to 255 entries, so the ceiling tracks the live array length (a cap of 256 would overrun it in `GameServer.disconnect` and throw on every disconnect). On current builds the cap therefore usually resolves to the vanilla 255 and the patch's remaining value is the metrics publication and regression guard. If RakNet refuses to start with a raised cap the factory logs an error and retries with the vanilla value, so the raise can never keep a server down. Boot verification: look for `Storm: RakNet incoming-connection cap` (raised or left-at-vanilla variant) in the server log — its absence means the running server is not executing this build. The extra sockets cannot become extra players: `LoginPacket` still rejects past `MaxPlayers` with `AccessDenied "ServerFull"`, and `GameServer.getPlayerCount()` counts assigned `playerIds`, not sockets — the headroom only converts a silent RakNet-level refusal into a handled "server is full" or a login-queue position. 256 is a hard ceiling because `UdpEngine.decode()` reads the per-connection index off the wire as `buf.getByte() & 255` into a fixed `UdpConnection[256]`. The third half of the fix is making the failure *visible*, since vanilla exports nothing that counts the pre-spawn population: `StormConnectionStageMetrics` publishes `storm_connections{stage}` across the ten stages of the login pipeline plus `storm_connection_slots_used` / `_slots_max` / `_raknet_peers`, and `ConnectionManagerLogPatch` turns PZ's `connections` log into `storm_connection_events_total{source,event}` so accepts-that-never-became-logins is a subtraction. Note the server can never count refusals directly — `ID_NO_FREE_INCOMING_CONNECTIONS` is only ever *received*, and only by clients. See [Metrics](metrics.md#connection-lifecycle--login-funnel).
- **Server browser says 85/100 while joiners are refused with "server is full"** — the count players see and the count the login gate enforces are different populations. The gate (`LoginPacket.processServer`, and `LoginQueue.getCountPlayers()` when the login queue is enabled) compares `GameServer.getPlayerCount()` against `MaxPlayers` — and `getPlayerCount()` counts every connection whose `playerIds` slot is assigned, which happens at login *grant* (`receiveClientConnect`), so the whole post-grant pipeline counts: clients downloading the world, players parked on character creation. The advertised count is the Steam game server's user list, which vanilla feeds only at character *spawn* (`receivePlayerConnect` → `SteamGameServer.AddPlayer`) and drains on disconnect and role changes. On a busy server the pipeline holds 10–20 connections, so the in-game browser and every A2S consumer (BattleMetrics and friends) show e.g. `85/100` while the gate correctly refuses at `103 >= 100` — and players report "it says full but it isn't". Storm makes the advertised number the whole held population: `SteamPlayerListReconciler` (swept once per tick from `ServerTickAdvice`, main thread) diffs the Steam user list against spawned players first, then pre-spawn connections, then players waiting in the login queue. Queue-waiters have no player id yet (`receiveClientConnect` hasn't run), so their entries use synthetic ids allocated downward from 1023 — a range real ids (`slot*4+playerIndex`, slot below the RakNet cap) can never reach — and swap to the real id under the same username at login grant; A2S exposes names, not ids, so BattleMetrics-style consumers see one continuous session across the swap. The queue pass matters below capacity too: admission is serialized through `currentLoginQueue`, so a joiner burst otherwise reads `85/100` while 15 people sit in line. Everything is **clamped at `MaxPlayers`**. The clamp is load-bearing: `MultiplayerUI.lua`'s anti-spam filter silently delists any server advertising `players > maxPlayers`, so a full pipeline reads as exactly `100/100`, never `103/100`. While the reconciler is active it is the list's single writer — `SteamGameServerPlayerListPatch` suppresses the vanilla `AddPlayer(IsoPlayer)`/`RemovePlayer(IsoPlayer)` wrapper bodies (the native's duplicate-id behavior is unknowable from Java), with spawn/disconnect/`HideFromSteamUserList` effects re-derived on the next sweep; `UpdatePlayer` (zombie-kill scores) still flows vanilla. Any native failure logs, best-effort removes the pre-spawn entries only Storm knows about, hands spawned entries back to vanilla's disconnect path, and stays off for the rest of the run. Steam mode only — non-Steam servers already report the pipeline-inclusive `getPlayerCount()` via `PublicServerUtil`. Rollback: `-Dstorm.steam.advertisePipelinePlayers=false`. Boot verification: `Storm: Steam advertised player count now covers the login pipeline (… clamped at MaxPlayers=<n>) …` in the server log on the first active tick. Observability: `storm_steam_advertised_players` in [Metrics](metrics.md#connection-lifecycle--login-funnel). What this does *not* change: the queue UI (`QueuePacket` already sends queued clients the pipeline-inclusive `countPlayers`/`maxPlayers` plus their queue position) and the in-game scoreboard (spawned players only, by design).
- **`GeneralActionPacket.setReject()`** — populates `playerId` from the `UdpConnection` (vanilla leaves it `-1`, so reject responses never resolve an owner).
- **`NetTimedActionPacket` accept/reject** — serializes the server-side action instead of the inbound packet, so clients receive the correct state and duration on the response.
- **First-aid health panel dead after respawn or a connection blip** — the vanilla client resets its own online id to `-1` in `GameClient.sendPlayerConnect` (initial connect *and* respawn) and `GameClient.disconnect`, and the first-aid UI (`ISHealthPanel`, `ISMedicalCheckAction`) can send `BodyDamageUpdatePacket START_UPDATING` inside that window. The server then registers a `BodyDamageSync.Updater` streaming to recipient `-1`: it ticks every 500 ms forever, sends to nobody (the connection lookup for `-1` is always null), can never be stopped (the matching `STOP_UPDATING` also carries `-1`), and the doctor's health panel silently shows nothing. Storm repairs the packet at parse time (`BodyDamageUpdatePacketPatch`): vanilla `PlayerID.parsePlayer` has already resolved the real player from the *sending connection* whenever the wire `playerIndex` isn't `-1`, so a wire id of `-1` with a resolved player is rewritten to that player's real online id — the resolution comes from the connection, so a spoofed id can't steer it, and packet-level ownership guards running at `processServer` (e.g. anti-cheat mods) see the repaired id instead of flagging the race as a spoof. Separately, `BodyDamageSyncPatch` guards `startSendingUpdates` against ids that don't resolve: a patient who disconnected in flight NPEs vanilla (`IDToPlayerMap.get` is dereferenced unchecked), and an unresolvable recipient (unpatched or hostile client) would still leak a dead updater.
- **`AnimalInventoryItem` null on save** — `CompressIdenticalItems` filters null-animal entries before save, removing a frequent crash during world unload.
- **Null-`adef` animal NPEs** — guards on `IsoAnimal.update`, `canClimbStairs`, `reattachBackToMom`, `IsoMovingObject.isPushedByForSeparate`, and `BaseVehicle.save` for animals whose definition failed to resolve (broken mod packs, missing animal types).
- **"CRC mismatch" log spam + redundant chunk writes from shared-CRC32 races** — the chunk-save pipeline shares two `CRC32` instances across threads. `ServerChunkLoader$SaveChunkThread.addLoadedJob` serializes the chunk on the *calling* thread with the thread object's single `crc32`; during `ServerMap.SaveAll` with ≥10 loaded cells, four `WorkerThread`s call it concurrently, interleaving reset/update on that one instance so a fraction of every periodic save's chunks get a garbage checksum embedded in the chunk file header — every later load of those chunks logs `CRC mismatch save=... load=...` from `sanityCheck.checkCRC` (log-only; chunk bytes are task-local and correct, so no data is harmed). Separately, `SaveLoadedTask.save()` computes the whole-file CRC through the outer shared `crcSave`, raced between the SaveChunk thread's run loop and the LoadChunk thread (`saveNow` runs matching queued tasks inline before each chunk load); garbage there pollutes the `ChunkChecksum` dedup cache, causing redundant disk writes and redundant chunk resends to clients. `SaveChunkThreadCrcRacePatch` / `SaveLoadedTaskCrcRacePatch` redirect the field reads to a per-thread `CRC32` (`StormChunkSaveCrc`) — every consumer sequence starts with `reset()`, so per-thread reuse is exact. Server-only.
- **Vehicles carrying animals permanently deleted by a boot-time thread race** — `GameServer.main` starts the `ServerPlayersVehicles` worker thread (SPVThread, vehicle streaming every 500 ms) *before* the multi-second `refreshAnimSets(true)` pass. When the thread loads a vehicle carrying an animal, `IsoAnimal.init → AnimationSet.GetAnimationSet → AnimState.Parse → AssetManager.load` puts into the same unsynchronized `HashMap`/`THashMap`s the main thread is filling; the maps corrupt (`ArrayIndexOutOfBoundsException` in `THashMap.rehash`), and `VehiclesDB2$QueueLoadChunk.vehicleLoaded` reacts to *any* load exception by **deleting the vehicle from vehicles.db** — animal trailer gone for good. Storm serializes the racing paths: a shared `ReentrantLock` around `AnimationSet.GetAnimationSet`/`Reset` and the whole of `refreshAnimSets` (`AnimationSetLockPatch`, `RefreshAnimSetsLockPatch` — one re-entrant lock because the refresh calls `GetAnimationSet` internally and iterates the asset table caller-side), plus `ACC_SYNCHRONIZED` flags on the map accessors `ActionGroup.getActionGroup`/`reloadAll` and `AssetManager.load`/`get`/`destroy`/`removeUnreferenced`/`enableUnload` (`ActionGroupSyncPatch`, `AssetManagerSyncPatch`). Steady-state cost is noise — the lock paths run at asset-load frequency, and the one hot method (`getActionGroup`, per zombie per tick) measures ~3 ns/call of uncontended monitor overhead. Server-only.
- **Kicked to the main menu after building a room (stale gutted-`IsoRoom` references)** — every build change makes `WorldRegionToMetaGrid` tear down and rebuild all player-built rooms in the cell; the teardown guts the live `IsoRoom` in place (`def = null`, building/squares cleared) while squares outside the dirty-chunk re-stamp sweep keep a cached reference to it (the room's square back-ref list is only filled on chunk load, and room IDs are renumbered by list index each rebuild). Consumers that skip vanilla's own `hasRoomDef()`-style null check then NPE — seen live in the FMOD `FirearmRoomSize` parameter, which recomputes every tick for the local player, surfaces the NPE at `IngameState.updateInternal`, and exits the world (audio dies, one error, back to the main menu). `IsoGridSquareGetRoomNullDefGuardPatch` guards the chokepoint: `IsoGridSquare.getRoom()` returns `null` for a gutted room, routing every consumer onto its vanilla no-room fallback — for player-built rooms that's the `IsoWorldRegion.isPlayerRoom()` branch, so e.g. firearm audio gets the region's real room size.
- **Idempotent `SpriteConfig.onAddedToOwner()`** — skips re-init if already initialized, so sync packets do not re-reset sprite state mid-game.
- **Case-insensitive whisper** — `ChatServer.processWhisperMessage` matches usernames case-insensitively and resolves to the canonical username (vanilla silently drops whispers when capitalization differs).
- **Failed workshop downloads are diagnosed and retried instead of crashing with no explanation** — a subscribed workshop item that Steam cannot download (hidden, unlisted, or removed item, or the temporary "Failed to get manifest request code, 'Access Denied'" window anonymous game-server logins hit right after an item updates) crashes vanilla with an NPE: the install-fail branch calls `ZomboidFileSystem.deleteDirectory(GetItemInstallFolder(id))` and `GetItemInstallFolder` returns null when the item was never installed. Storm null-guards `deleteDirectory`, then on install failure asks Steam's anonymous Web API (one batched `GetPublishedFileDetails` call) for each missing item's status and logs a per-item verdict (`StormWorkshopItemProbe`), retries the install 3 times 20 s apart to ride out the transient post-update deny-window, and if it still fails prints a banner with each item's ID, title, page URL, diagnosis, and remediation before letting startup fail (`StormWorkshopInstallRecovery`). The server never starts without its configured workshop items, matching vanilla — the difference is the log now tells you which item is failing and what Steam says about it.
- **Translator "Missing arguments" spam on the loading-queue screen** — vanilla call sites wrap a no-arg `getText` in an outer `String.format` (`LoadingQueueUI.render()`: `String.format(Translator.getText("UI_GameLoad_windSpeed"), windName, knots, kph)`). Formatting a text containing `%1$s` with zero arguments is guaranteed to throw `MissingFormatArgumentException`, warn-log, and fall back to returning the raw text — once per rendered frame, hundreds of warnings per second while a player waits in the login queue, which drowns real diagnostics out of log bundles. `TranslatorPatch` detects the guaranteed-throw shape (zero args, text contains `%1$s`) in `reportMissingArgumentsFromPastAbuse` and returns the raw text directly — the same string vanilla's catch path produces, minus the exception and the log line. Calls with arguments and zero-arg texts without positional specifiers are untouched.
- **`Map.MapAllKnown` stopped revealing the map in multiplayer (42.20.3)** — until 42.20.2 the server pushed a joining player's visited data with `PlayerVisitedPacket`, whose `processClient` overwrote the client's `visited` array *and then* re-applied the sandbox option (`if (mapAllKnown) instance.setKnownInCells(metaGrid.minX, …, metaGrid.maxY)`). 42.20.3 replaced that packet with `RequestDataPacket.RequestID.PlayerVisited` → `WorldMapVisited.receiveRequestData`, which inflates the server's per-user bytes straight over the whole array and **dropped the re-apply** — the client's own all-known pass (in `WorldMapVisited.getInstance`) has already run by then, so the transfer wipes it and the map shows only where the player has actually been, on a server configured to reveal everything. Storm fixes it server-side, so vanilla clients are fixed too: `WorldMapVisitedServerAllKnownPatch` routes `WorldMapVisitedServer.sendRequestData` through `StormMapAllKnownSend`, which — only while the option is on — sends a copy with `BIT_KNOWN` set on every unit. Visited bits are preserved (OR, exactly like vanilla's `setKnownInCells`), and the copy is transient: the stored per-user data on disk is never rewritten, so turning the option back off returns players to their real explored map instead of leaving it permanently revealed. Any failure logs once and falls back to the vanilla body for the rest of the run.
- **Admin brush-tool tiles vanish on chunk reload** — vanilla `ISBrushToolTileCursor:create()` runs entirely on the placing client and `placeMoveableInternal` never transmits generic tile objects to the server (only floor tiles and wall overlays have an `isClient()` transmit branch), so admin-placed tiles exist only in the client's local chunk copy and disappear when the area unloads and reloads. `server/StormBrushToolFix.lua` routes the placement through `sendClientCommand`; the server (gated on `Capability.UseBrushToolManager`) re-runs the vanilla create logic, which transmits the object to all clients and persists it in the server's chunk save.

## Mod-loader extensions

- **Mod jars on the classpath** — every `.jar` inside a mod's version-specific directory (e.g. `42/`) is loaded into `StormClassLoader` and scanned for a `ZomboidMod` entry point.
- **Lua auto-injection from jars** — any `lua/` directory inside a mod jar is registered into the game's Lua environment on `OnZomboidGlobalsLoad`, so a Storm mod ships its client/server/shared Lua next to its Java code in the same jar.
- **Annotation-driven HTTP / event / command surfaces** — mods register HTTP endpoints (`@HttpEndpoint`), event handlers (`@SubscribeEvent`), client-command handlers (`@OnClientCommand`), and server console commands (`StormCommandRegistry.MOD_COMMANDS`) without touching vanilla wiring.
- **`io.pzstorm.storm.halo.StormHalo`** — Java API to draw a temporary speech bubble over a player's head from server-side mod code (`setHalo(target, text)`, `setHalo(target, text, r, g, b)`, `setHaloFor(viewer, target, text)`). Backed by `client/StormHalo.lua` and PZ's native `IsoGameCharacter:addLineChatElement`, so bubbles render over remote players with no chat-log entry.
- **`PersistedBooleanConfigOption`** — subclass of vanilla `BooleanConfigOption` that auto-persists its value to `~/Zomboid/Storm/persisted-map-config-options/<name>.json` and reloads on construction. Drop-in replacement for mods that need a per-server toggle.
- **`StormUtils.getTextureResourceFromStream(name, classLoader)`** — load a PZ `Texture` straight from a jar resource without staging it on disk first.
- **`StormPrometheus.registry()`** — shared `PrometheusRegistry` for mod metrics; instruments registered here are scraped at `/metrics` alongside Storm's own (see [Prometheus Metrics](metrics.md) for naming conventions).
- **FMOD JNA bindings** — `io.pzstorm.storm.jna.fmod.FmodJNA` exposes the running game's FMOD system handle, 3D listener / channel attributes, cone settings, and custom roll-off curves via JNA, so mods can drive native audio without re-binding the library or shipping their own copy.
- **LuaLS type-stub dump** — every Java class exposed to Lua is written out as a LuaLS-compatible stub under `lua_stubs/` so IDEs can lint Lua against the live game API.

## Client-side behavior

Player-facing conveniences come in two forms. Most are Lua files shipped inside
Storm's jar under `media/lua/client/`; they reach connected players through the
vanilla mod-distribution flow and talk back to the server over
`sendClientCommand`. Clients started through the [Storm Launcher](launcher.md)
additionally run Storm itself (the launcher passes the agent flags), which
enables Storm-core client Java features:

- **Server-item mod-dir pinning** — `io.pzstorm.storm.client.StormServerModDirs`
  (always registered on Storm clients). Vanilla resolves each mod id to a folder
  with a global first-wins walk over *every* installed workshop item, so a local
  item the server doesn't use — a mega-pack, an old re-upload, a deleted/private
  item Steam can no longer update — can shadow the server's copy of a mod and
  produce an unfixable join-time checksum kick naming a file inside the wrong
  item. On every Steam-mode connect (`OnServerWorkshopItems` "Success", fired
  after the server's items are installed/updated and before `CheckMods`
  resolves mod dirs) Storm reads the server's item list from the login payload,
  scans those items' `mods/` folders, and force-pins `modIdToDir` so the
  server's own copies are what the client checksums and loads; the pins are
  re-applied at every `loadMods` entry because connect-time `Reset()` clears
  the map. Server mods living outside workshop items (manual installs, staged
  dev folders) still resolve vanilla. If a pin had to *override* a boot-time
  resolution, the connect-time fast ResetLua declines and the vanilla reload
  rebuilds from the corrected dirs. Fails soft: any error leaves vanilla
  resolution untouched.

- **Launcher auto-join** — `io.pzstorm.storm.client.LauncherAutoJoin`
  (registered only when the launcher passes `-Dstorm.autojoin.file=<path>`)
  reads and immediately deletes the launcher's one-shot credential handoff at
  the first main menu, then fills and submits the vanilla `ServerConnectPopup`
  from Java-driven Lua — a zero-click path from launcher to in-game. Without
  the property the class is never registered, so manual game starts are
  unaffected.

- **Low-RAM detection popup** — `client/StormRamAllocation.lua` reads the joining player's `-Xmx` value, reports it to the server (populating `GET /storm/ram-allocations`), and pops up a "your game has <4 GiB allocated, consider `-Xmx8g --`" warning with a "don't show again" tickbox (persisted to `StormRamAllocationSettings.txt`). If a player with ≤ 3221 MB allocated complains about lag in chat ("lag", "stutter", "freezing", "fps", …), the server detects it via a server-side patch on `ChatServer.sendMessage` (dispatching `OnServerChatMessageEvent`), broadcasts a reminder to server chat, and re-opens the popup on that player's screen (at most once per 5 minutes per player).
- **Storm column on the Players scoreboards** — `src/main/resources/lua/client/storm/StormPlayersScoreboard.lua` (injected from storm.jar after each `LuaManager.LoadDirBase()`, so it is not part of the server's client-file checksum) adds a right-aligned "Storm <version>" / "No Storm" label to every row of the ESC-menu PLAYERS scoreboard (`ISScoreboard`, admins only) and the Admin Panel Mini Scoreboard (`ISMiniScoreboardUI`). Each Storm client announces its version once with the `StormPlayers.hello` client command on the first tick after `OnGameStart` (`IngameState.enter` fires `OnGameStart` before it sends `PlayerConnect`, so a hello sent from the event itself is dropped by `GameServer.receiveClientCommand` as "player is null"); `io.pzstorm.storm.connection.StormPlayersHandler` records it per RakNet connection guid in `StormClientVersionRegistry` (falling back to the game-port TCP handshake's `clientStormVersion`). On every `OnScoreboardUpdate` an admin client holding `Capability.SeePlayersConnected` sends `StormPlayers.request` (throttled to 1/s) and the server replies asynchronously with a `StormPlayers.list` server command carrying `{ [username] = version }`; until that first reply arrives nothing is drawn, so the column is invisible against non-Storm servers. Vanilla clients never send the hello and show as "No Storm". - **Bootstrap verification** — `client/StormBootstrapVerification.lua` logs a one-line confirmation to the connected player's log that Storm-shipped Lua loaded, so a misconfigured server is visible from the player's console without enabling debug logging.
