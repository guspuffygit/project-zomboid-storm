# What Storm Changes

Beyond loading mod jars, Storm rewrites a chunk of the game's bytecode at load
time to fix vanilla bugs, expose runtime tunables, dispatch events, and lift
hardcoded performance limits. Everything below is gated to the dedicated-server
JVM unless noted, and is always-on unless it points at a tunable flag in
[Server Configuration](server-configuration.md).

## Performance

- **Parallel server-LOS pipeline** — `ServerLOS` fans out across `1..16` worker threads (`Storm.ServerLosThreads` sandbox option); per-square LOS state, lighting arrays, and scratch vectors are made thread-safe and per-worker. Each worker owns a slot in the resized `LosUtil.cachedresults[]` so the vanilla per-square cache is reused instead of reallocated; concurrent `IsoRoom.onSee` dispatch is serialized through a single reentrant lock so room-discovery side effects stay deterministic.
- **Stride-based animal LOS** — `Storm.AnimalLOSTickInterval` distributes `IsoAnimal.updateLOS` across N ticks; `0` disables animal LOS entirely on servers where it isn't worth the cost. Side effect: `BaseAnimalBehavior.spotted()` — the sole award path for animal-sourced Tracking/Sneak/Nimble/Lightfoot XP — only runs from this scan, so stride N also divides that XP by N (`0` = none).
- **Stride-based virtual-animal simulation** — `Storm.VirtualAnimalTickInterval` runs the whole `AnimalZones.updateVirtualAnimals()` pass every Nth tick, raising `GameTime.perObjectMultiplier` to N on executing ticks so time-delta-driven movement and track expiry advance the skipped time in one step (vanilla's own bucket-scheduler compensation mechanism). `0` freezes virtual animals entirely.
- **Stride-based zombie ownership rescans** — `Storm.ZombieAuthTickInterval` strides the *unowned*-zombie path of `NetworkZombieManager.updateAuth()`: vanilla bypasses its 2 s gate whenever a zombie has no owner and re-runs the full O(connections × players) relevance scan every tick for every such zombie. Owned zombies keep the vanilla 2 s cadence untouched.
- **Stride-based inventory-item GC** — `Storm.InventoryItemSweepTickInterval` runs the idempotent orphaned-item sweep in `InventoryItemSystem.update()` every Nth tick instead of every tick.
- **O(1) cell-membership operations** — replaces vanilla's `ArrayList.contains()` / `remove(Object)` scans on the per-cell process queue, static-updater list, and removal list with sidecar hash indices. Dominates main-thread cost on chunk-unload bursts (see `CellAddToProcess*`, `IsoObjectStaticUpdaterRemoveSubst`, `CellProcessIsoObjectFlush`).
- **O(1) `ServerLOS.findData(IsoPlayer)`** — vanilla scans an `ArrayList<PlayerData>` by reference per call, dominating `IsoPlayer.updateLOS()` on busy servers. Storm caches the lookup in an identity-keyed sidecar (`ServerLOSPlayerDataCache`, a lock-free `ConcurrentHashMap` so the per-call `get` takes no monitor).
- **Distance-culled player LOS scan** — vanilla `IsoPlayer.updateLOS()` walks *every* moving object in the loaded cell (thousands on a busy server) per player per tick, running a `ServerLOS.isCouldSee` lookup plus client-only bookkeeping (fade-in alpha targets, `musicZombies*` music-intensity fields, jump-scare state) that is not `bServer`-gated and that no server-side code reads. Storm skips objects outside the player's 96×96-square visibility cube before any cast/visibility work (outside it `isCouldSee` is always false and the vanilla body has zero server-visible effect), reads the visibility cube directly instead of doing a per-object map lookup, and strips the client-only writes. Zombie spotting (`TestZombieSpotPlayer` on both the lit and could-see branches), `TestIfSeen`, panic/boredom counters, and `lastSpotted` maintenance are vanilla-exact. ~18% of main-thread CPU at 79 players. Disable with the `Storm.PlayerLosFastPath` sandbox option; auto-reverts to vanilla permanently if the fast path ever throws.
- **Registry-backed in-use-entity sweep** — vanilla `UsingPlayerUpdateSystem.update()` null-checks *every* entity in the engine's iso-object bucket (123k+ on a busy server) each tick to find the handful whose `usingPlayer` is non-null (roughly the number of players with a crafting/entity UI open) and release them once the player leaves a ±10-tile box, changes Z level, or dies. Storm maintains an identity registry of exactly those entities — fed unconditionally from `GameEntity.setUsingPlayer` and the server branch of the `receiveUpdateUsingPlayer` entity packet (which bypasses the setter) — and sweeps only the registry, clearing through the real `setUsingPlayer(null)` so the vanilla client broadcast still fires. Release rules are vanilla-exact; entries whose entity left the engine (chunk unload) are evicted without touching world state. ~6% of main-thread CPU at 79 players. Disable with the `Storm.UsingPlayerSweepFastPath` sandbox option (safe to flip live — the registry stays complete while off); auto-reverts to vanilla permanently if the sweep ever throws.
- **Hoisted, reordered fluid-container pass** — vanilla `FluidContainerUpdateSystem.updateSimulation()` visits every registered FluidContainer entity on every 100ms simulation tick (plus uncapped catch-up ticks) and, per entity, re-reads `ClimateManager` precipitation state and the sandbox day length, and runs `getPrimaryFluid()` (a fluid-list scan) plus a `"Petrol"` string compare before the cheap rain guards; only the network sync is throttled, not the scan. Storm hoists the per-tick invariants (precipitation intensity/is-snow, day-length divisor, game-seconds-per-tick) out of the loop, evaluates the branches' shared cheap prefix (`canPlayerEmpty && rainCatcher > 0`) first so non-qualifying entities skip the fluid-list scan, and compares the petrol fluid by `FluidType` identity instead of by string (provably equivalent — modded fluids can never carry the builtin name). Rain fill, snow halving, petrol evaporation, and `objectSyncLimiter`-throttled syncs are vanilla-exact, in vanilla order. ~6% inclusive of main-thread CPU at 79 players. Disable with the `Storm.FluidContainerUpdateFastPath` sandbox option; auto-reverts to vanilla permanently if the fast path ever throws.
- **Memoized ECS component-class lookup** — the static `ECSComponent.getECSClass(Class)` walks the superclass chain up to `ECSComponent` on every call, and it sits under every `getECSComponent`/`hasECSComponent`/`removeECSComponent` (per character per tick via `getStateMachine()` and AI lookups — millions of calls/second, ~2.9% self time at 79 players). The walk is a pure function of the class, so Storm memoizes it in a `ClassValue` (JVM-optimized, weakly referenced, classloader-safe) whose compute encodes the identical loop — results match vanilla for every input, including `null` and `ECSComponent.class` (both routed to the vanilla body, which returns `null`). Disable with the `Storm.EcsClassCache` sandbox option (always safe to flip live); auto-reverts to vanilla permanently if a lookup ever throws.
- **Budgeted cell unloads** — vanilla `ServerMap.postupdate()` destructively unloads *every* loaded cell that fails the relevance check in a single tick; each `ServerCell.Unload()` walks 64 chunks → `IsoChunk.removeFromWorld()` → per-entity engine unregistration, so a burst of stale cells (players logging off or moving together) turns into one multi-hundred-ms tick spike (~11% of the main thread during a burst window at 79 players, near-zero steady-state). Storm replaces the loop with a faithful reimplementation that unloads at most `Storm.CellUnloadBudgetPerTick` cells per tick (default 2); stale cells beyond the budget stay in `loadedCells` and are re-evaluated next tick, so a cell that becomes relevant again is naturally kept and a stale one unloads a few ticks later. Every side effect of the cells it does unload is vanilla-exact and in vanilla order: the cancel-loading bookkeeping for in-flight cells, `cell.update()` for relevant cells, the `ServerLOS.instance.suspend()`-before-first-unload / resume-in-finally bracket, the `catch (Exception)` swallow, and the `NetworkZombiePacker.postupdate()` / `chunkLoader.updateSaved()` tail. Deferral is safe: `loadedCells` is bounded by player relevance, `SaveAll`/`QueuedSaveAll` save deferred cells like any other loaded cell, and `ServerCell.Unload` queues its chunk save jobs whenever the cell eventually unloads. Set the option to `0` to restore vanilla; auto-reverts to vanilla permanently if the budgeted body ever throws. Composes with cell warming (`-Dstorm.cells.keepWarm`): when warming is on, the warm pass owns `postupdate` and the budget defers to it.
- **O(1) entity unregistration** — `EngineEntityManager.removeEntityInternal` removes each departing entity from the engine's global entity array via `Array.removeValue`, a linear identity scan of ~123k live entities (3.1% main-thread self time during cell-unload bursts — the dominant per-entity cost under `IsoChunk.removeFromWorld`). The array is unordered, so vanilla's removal is already swap-with-last O(1) — the cost is purely the index search. Storm maintains an identity index (entity → position) fed from the array's only two mutation sites (the single-arg `add` in `addEntityInternal` and `removeValue` in `removeEntityInternal` — the field is private and never leaked mutably; world reload constructs a fresh array that a constructor hook re-tracks) and removes by index lookup + swap fixup instead of scanning. Before using an index it verifies the slot actually holds that entity; any mismatch falls back to the vanilla scan and latches the fast path off permanently, so a wrong removal is impossible. Disable with the `Storm.EntityRemoveFastPath` sandbox option (safe to flip live; re-enabling rebuilds the index once).
- **Chunk-windowed zombie-sight vehicle occlusion** — vanilla `IsoZombie.isVehicleBetween` iterates *every* vehicle in the loaded cell per zombie sight test, inverting each vehicle's world transform twice, even when the result is provably unused (spot `chance` already zero, or the target sits in a vehicle). Storm skips the scan entirely in those cases and otherwise tests only vehicles registered in the chunks overlapping the ≤20-tile sight segment, with a cheap center-vs-segment reject before the vanilla-exact OBB intersection. ~14% of main-thread CPU on a vehicle-heavy server. Disable with the `Storm.ZombieSightVehicleFastPath` sandbox option.
- **Configurable server tick rate** — `Storm.ServerFps` lifts the hardcoded 10 TPS cap and sets the main-loop tick gate, `PerformanceSettings.getLockFPS()` on the server, and the `IsoPhysicsObject.update()` FPS scalar from a single value.
- **Tick-rate-aware random rolls** — `RandInterface.AdjustForFramerate` hardcodes a 10-TPS scalar on the server, so at `Storm.ServerFps > 10` every per-tick random event (fire spread, wound infection, footstep noise, drunk stumbles, ambients, vehicle engine auto-stall since 42.20.0) would fire `fps/10`× too often per real second. Storm rescales by the live lock fps (`chance * fps / 30`); bit-identical to vanilla at 10 TPS.
- **`VehicleManager.serverUpdate` waste removal** — vanilla iterates the entire vehicle set for each of the 512 connection slots even when a slot never held a connection, and the method runs twice per frame (`GameServer.main` + `IsoWorld.update`). Storm replaces it with a null-slot-skipping version that runs once per frame; the rate-gated send block is unchanged. Disable with `-Dstorm.vehicleupdate.optimize=false`.
- **Non-boxing `Stats.get(CharacterStat)`** — eliminates per-frame `Float` autoboxing on the hottest character-stat accessor.
- **Skip server-side electricity scan** — `IsoGenerator.update` stops iterating chunk tiles on the server (the result is only used by the client UI); chunk-position bookkeeping is used instead. The full scan still re-runs once per in-game hour per activated generator so `totalPowerUsing` (the fuel-drain rate) tracks load changes between activations — e.g. 42.20.0's light switches, which register as generator loads and toggle at dusk/dawn.

## Behavioral overrides

- **Packet rate limit disabled on the server** — `PacketsCache.isLimitExceeded(...)` is short-circuited, so the vanilla `ServerOptions.maxPacketsPerSecond` cap does not apply to inbound or outbound traffic.
- **Net-data drain cap** — `GameServer.mainLoopDealWithNetData` (HIGH + player-update + vehicle inbound drain) gets a per-outer-loop-spin wall-clock cap from `Storm.NetDataCapMs` (default 90 ms; `0` disables). When the cap fires, subsequent packets in the same spin are short-circuited (dropped — RakNet already ACKed them on receipt, so nothing is retransmitted regardless of declared reliability; periodic state is regenerated next tick, one-shot packets are lost — the same tradeoff as vanilla's 70 ms vehicle-queue drop) and the next spin starts fresh. Protects world-tick scheduling during reconnect storms; drops counted by `pz_netdata_deferred_total`.
- **Per-peer send-buffer watchdog** — `Storm.PeerSendBufferKickMb` (default 20 MB) and `Storm.PeerSendBufferKickHoldTicks` (default 50 ticks ≈ 5 s @ 10 TPS) auto-disconnect any peer whose HIGH-priority outbound RakNet queue stays above the threshold for the hold window. Bounds server-side memory growth caused by a peer on a saturated/lossy uplink that can't drain the broadcast firehose PZ queues for every `fullyConnected` peer. Setting MB to `0` disables the kick while leaving the per-peer telemetry gauges live (`storm_peer_*`). Auto-kicks are counted by `storm_peer_kicked_send_buffer_total`; the disconnect reason is `storm-send-buffer-overflow`.
- **Zombie culling — no longer patched (removed in 42.20.0)** — through 42.19.1 Storm carried two bytecode patches on `ZombieCountOptimiser` plus a `Storm.ZombieCullThreshold` sandbox option, because vanilla measured its cull budget against the whole map's zombie count, capped the option at 500 with a minimum of 10 (so culling could not be turned off), and never decremented its own budget (mass-deleting ~10% of the population per frame on overshoot). 42.20.0 rewrote that class and fixed all three, so the patches **and** the Storm option were deleted — set vanilla's `ZombieConfig.ZombiesCountBeforeDelete` directly. Storm still publishes the live value as `storm_zombie_cull_threshold`. See [server-configuration.md](server-configuration.md#zombie-culling-is-a-vanilla-option) for the upgrade note.
- **UUID-based item transfers** — `StormTransferHandler` replaces vanilla's per-player byte-ID `Transaction` system for player ↔ player / bag / world / vehicle-part transfers; floor drops and dead-body containers still use vanilla. Eliminates ID-wraparound collisions and the "vacuous truth on ID 0" reject bug. Driven from `client/StormTransferFix.lua` over `sendClientCommand("StormTransfer", ...)`.
- **Faster natural-water collection** — `StormFastFillNaturalWater` overrides `ISTakeWaterAction:getDuration()` so filling from rivers, lakes, and other natural sources finishes in 100 ticks instead of vanilla's much-longer pull (taps and rain barrels are unaffected).
- **Mod command dispatch** — `CommandBase.findCommandCls` and `getSubClasses` consult `StormCommandRegistry`, so mod commands resolve in chat and show up in `/help` alongside vanilla ones.
- **Custom child-JVM bootstrap** — `CoopMaster` is rewritten to launch hosted servers through Storm's agent instead of a bare `ProcessBuilder`, so in-game-hosted servers also load Storm.
- **Protected uncaught exception handler** — the handler Storm installs at startup cannot be replaced by mods or vanilla code that calls `Thread.setDefaultUncaughtExceptionHandler`, so crashes always route through Storm's log writer.
- **Event hooks** — packet receipt (`OnPacketReceived`), ban actions (`onBanUser` / `onBanIp` / `onBanSteamID`), chat messages, Lua VM init, world-map render, item-transfer completion, and ~190 Lua event bridges become subscribable from Java via `@SubscribeEvent`. See [Mod Author Guide](mod-author-guide.md).
- **Storm and Storm mod updates restart the server**: if Storm or a Storm mod updates, the server quits so the new files load on the next start.

## Bug fixes shipped with Storm

Each line below is a vanilla bug Storm patches out, all default-on.

- **Cross-player action cancel** — `ActionManager.removeFromQueue` filters by byte action id alone in vanilla, so cancelling your own action also yanks every other player's queued action with the same id. Patched to filter by `(byteId, onlineId)`.
- **Cross-player transaction cancel** — same shape on `ItemTransactionPacket`: one player's cancel rejects every other player's pending transfers in vanilla. Patched to filter by `(byteId, onlineId)`.
- **Stale transaction cascade** — `TransactionManager`'s consistency check rejects every new transfer after a container unloads mid-flight in vanilla; the patch sweeps stale transactions before the check.
- **Transaction byte-ID wraparound + ID-0 vacuous truth** — the vanilla `Transaction` allocator hands out 8-bit ids that wrap and collide across players, and `createItemTransaction` returns `0` on failure, which then matches every "no transaction" check downstream. Replaced by `StormTransferHandler`'s UUID-keyed protocol for player / bag / world / vehicle-part transfers.
- **Zombie id collisions ("zombie mitosis")** — vanilla's free-running 16-bit allocator wraps and reuses live ids on high-population servers; replaced with hash-probed allocation in `IsoObjectIDAllocate`.
- **Zombie map invariant** — `IsoZombie.update` re-establishes "`onlineId != -1` ⇒ in `ServerMap.zombieMap`" every tick, so chunk-load zombies stay in authoritative state.
- **Pop-cell save append accumulation** — `IsoChunk.removeFromWorld` calls `ZombiePopulationManager.requestSaveCell` on every chunk unload, and the native `n_saveCell` appends each snapshot to `Saves/.../zpop/zpop_X_Y.bin` rather than overwriting it, so the same live zombie's 12-byte record accumulates dozens of copies in the same file as a player roams a pop cell. On the next reload, native emits every accumulated copy and N visually identical zombies spawn at the same square with sequential online ids — the cluster-of-clones behavior players colloquially call "zombie mitosis," distinct from the id-collision bug above. Storm short-circuits `requestSaveCell` on the dedicated server (`RequestSaveCellSuppressPatch`); the global autosave path that writes `zpop_virtual.bin` is independent and persists live zombies on the normal cadence. **Caveat:** the patch prevents new dupes from being written, but existing `zpop_X_Y.bin` files on disk still hold accumulated copies and will keep spawning clones on cell load until the on-disk files are cleaned (delete to regenerate from descriptors, or dedup in place).
- **Mid-handshake relevance leak (zombies at world origin)** — `UdpConnection`'s constructor initializes `releventPos[0] = new Vector3()` with default `relevantRange = 0`. Until the client's first `PlayerPacket` fires (typically 30+ s into the world-download handshake), the connection's stored "player position" is exactly `(0,0,0)`. `ServerMap.outsidePlayerInfluence` iterates every connection without filtering on `isFullyConnected()`, so the four ServerCells whose corners touch world `(0,0)` — `(0,0)`, `(0,-1)`, `(-1,0)`, `(-1,-1)` — claim relevance during every handshake. Cell `(-1,-1)` is suppressed by an unrelated guard; the other three stay in `loadedCells`, `LoadedAreas(serverCells=true)` reports them to the native pop manager, and virtual zombies materialize into the empty origin terrain. Storm short-circuits the four `UdpConnection` relevance methods (`isRelevantTo`, `RelevantToPlayerIndex`, `RelevantTo`, `getRelevantAndDistance`) to return "not relevant" whenever `isFullyConnected()` is false (`UdpConnectionRelevancePatch`), so handshaking connections do not force origin cells loaded. **Caveat:** the patch prevents further accumulation, but zombies already materialized at origin remain — clean them up server-side with `cell:getZombieList()` + `:removeFromWorld()`/`:removeFromSquare()` filtered by radius.
- **Everyone stuck on "Getting Server Info..." once a server gets busy** — two independent vanilla defects compound into a server that silently stops accepting anyone. First, `GameServer.startServer` builds the RakNet peer with a **hardcoded** cap of 101 incoming connections (`new UdpEngine(defaultPort, udpPort, 101, serverPassword, true)`) and never consults `MaxPlayers`; since `ServerOptions.getMaxPlayers()` is itself capped at 100, a full-size server has *one* spare socket for its entire login pipeline. Second, the only reap path for stalled logins — inside `GameServer.main`'s `updateDBCount > 150` block — is gated on `connection.getUserName() == null`, so a client that sent its username and then died anywhere later in the handshake (workshop init, mod check, chunk download, character creation) holds its slot **forever**; nothing else removes it, and RakNet's keepalive does not help because the peer stays responsive at the RakNet layer while the game-level handshake is dead. Leaked slots accumulate until the peer is full, at which point RakNet answers every new joiner with `ID_NO_FREE_INCOMING_CONNECTIONS` — a packet the vanilla client never handles (it exists only as a constant in `RakNetPeerInterface`), so there is no `OnConnectFailed`, no state change, and no timeout: `ConnectToServer.lua` keeps the last ZNet state label it was given and the player sits on **"Getting Server Info..."** indefinitely. Observed on a 100-slot production server: 12 unreapable connections aged 16–25 minutes pinning 99 of 101 slots, and every join attempt hanging. Storm fixes both halves server-side. `GameServerStalledConnectionReapPatch` sweeps from `launchCommandHandler` (called once per tick on the server main thread, so `disconnect` never runs off-thread; the sweep throttles itself to `-Dstorm.reapSweepIntervalMs`, default 30 s) and drops any connection that has not reached `isFullyConnected()` within `-Dstorm.reapStalledConnectionMs` (default 10 minutes) of a sweep first seeing it. The budget is wall-clock, not idle time: `setFullyConnected()` only fires when the character actually spawns (`receivePlayerConnect`), so this kicks both dead handshakes *and* players parked on the pre-spawn "Click Start" screen, even if their client keeps chattering at the packet level. Fully-connected players are never candidates; connections awaiting co-op approval, sitting in the login queue, or pending Google-auth get their clock re-stamped every sweep, so their budget only starts once the exempt state ends (note vanilla's `loginQueueConnectTimeout` merely *forgets* a timed-out `currentLoginQueue` without disconnecting it — the reaper is what actually frees that slot). Connections actively downloading chunks are likewise re-stamped: `PlayerDownloadServerChunkActivityPatch` marks every chunk-request wave as it arrives at `PlayerDownloadServer.getClientChunkRequest`, so a client legitimately spending longer than the budget streaming the world over a slow link is never kicked mid-load. That exemption matters beyond wasted progress — vanilla's loading thread races `GameClient.client` between `IsoWorld.init` and `IsoCell.LoadPlayer`, so *any* disconnect during the loading screen crashes an unmodified client with `NullPointerException: ... PlayerDB.getInstance() is null` instead of a "connection lost" message. Campers cannot hide behind it: a client that stops requesting chunks (spawn-screen idler, dead peer) goes quiet on this signal even while RakNet keepalive stays chatty, and its budget runs down normally. `GameServerConnectionCapPatch` substitutes the hardcoded `101` with `clamp(max(101, MaxPlayers + storm.raknet.connectionHeadroom), .., 256)` (default headroom 64, so a 100-slot server gets 164); if RakNet refuses to start with the raised cap the factory logs an error and retries with the vanilla 101, so the raise can never keep a server down. Boot verification: look for `Storm: RakNet incoming-connection cap raised 101 -> <cap>` in the server log — its absence means the running server is not executing this build. The extra sockets cannot become extra players: `LoginPacket` still rejects past `MaxPlayers` with `AccessDenied "ServerFull"`, and `GameServer.getPlayerCount()` counts assigned `playerIds`, not sockets — the headroom only converts a silent RakNet-level refusal into a handled "server is full" or a login-queue position. 256 is a hard ceiling because `UdpEngine.decode()` reads the per-connection index off the wire as `buf.getByte() & 255` into a fixed `UdpConnection[256]`. The third half of the fix is making the failure *visible*, since vanilla exports nothing that counts the pre-spawn population: `StormConnectionStageMetrics` publishes `storm_connections{stage}` across the ten stages of the login pipeline plus `storm_connection_slots_used` / `_slots_max` / `_raknet_peers`, and `ConnectionManagerLogPatch` turns PZ's `connections` log into `storm_connection_events_total{source,event}` so accepts-that-never-became-logins is a subtraction. Note the server can never count refusals directly — `ID_NO_FREE_INCOMING_CONNECTIONS` is only ever *received*, and only by clients. See [Metrics](metrics.md#connection-lifecycle--login-funnel).
- **Server browser says 85/100 while joiners are refused with "server is full"** — the count players see and the count the login gate enforces are different populations. The gate (`LoginPacket.processServer`, and `LoginQueue.getCountPlayers()` when the login queue is enabled) compares `GameServer.getPlayerCount()` against `MaxPlayers` — and `getPlayerCount()` counts every connection whose `playerIds` slot is assigned, which happens at login *grant* (`receiveClientConnect`), so the whole post-grant pipeline counts: clients downloading the world, players parked on character creation. The advertised count is the Steam game server's user list, which vanilla feeds only at character *spawn* (`receivePlayerConnect` → `SteamGameServer.AddPlayer`) and drains on disconnect and role changes. On a busy server the pipeline holds 10–20 connections, so the in-game browser and every A2S consumer (BattleMetrics and friends) show e.g. `85/100` while the gate correctly refuses at `103 >= 100` — and players report "it says full but it isn't". Storm makes the advertised number the whole held population: `SteamPlayerListReconciler` (swept once per tick from `ServerTickAdvice`, main thread) diffs the Steam user list against spawned players first, then pre-spawn connections, then players waiting in the login queue. Queue-waiters have no player id yet (`receiveClientConnect` hasn't run), so their entries use synthetic ids allocated downward from 1023 — a range real ids (`slot*4+playerIndex`, slot below the RakNet cap) can never reach — and swap to the real id under the same username at login grant; A2S exposes names, not ids, so BattleMetrics-style consumers see one continuous session across the swap. The queue pass matters below capacity too: admission is serialized through `currentLoginQueue`, so a joiner burst otherwise reads `85/100` while 15 people sit in line. Everything is **clamped at `MaxPlayers`**. The clamp is load-bearing: `MultiplayerUI.lua`'s anti-spam filter silently delists any server advertising `players > maxPlayers`, so a full pipeline reads as exactly `100/100`, never `103/100`. While the reconciler is active it is the list's single writer — `SteamGameServerPlayerListPatch` suppresses the vanilla `AddPlayer(IsoPlayer)`/`RemovePlayer(IsoPlayer)` wrapper bodies (the native's duplicate-id behavior is unknowable from Java), with spawn/disconnect/`HideFromSteamUserList` effects re-derived on the next sweep; `UpdatePlayer` (zombie-kill scores) still flows vanilla. Any native failure logs, best-effort removes the pre-spawn entries only Storm knows about, hands spawned entries back to vanilla's disconnect path, and stays off for the rest of the run. Steam mode only — non-Steam servers already report the pipeline-inclusive `getPlayerCount()` via `PublicServerUtil`. Rollback: `-Dstorm.steam.advertisePipelinePlayers=false`. Boot verification: `Storm: Steam advertised player count now covers the login pipeline (… clamped at MaxPlayers=<n>) …` in the server log on the first active tick. Observability: `storm_steam_advertised_players` in [Metrics](metrics.md#connection-lifecycle--login-funnel). What this does *not* change: the queue UI (`QueuePacket` already sends queued clients the pipeline-inclusive `countPlayers`/`maxPlayers` plus their queue position) and the in-game scoreboard (spawned players only, by design).
- **`GeneralActionPacket.setReject()`** — populates `playerId` from the `UdpConnection` (vanilla leaves it `-1`, so reject responses never resolve an owner).
- **`NetTimedActionPacket` accept/reject** — serializes the server-side action instead of the inbound packet, so clients receive the correct state and duration on the response.
- **`AnimalInventoryItem` null on save** — `CompressIdenticalItems` filters null-animal entries before save, removing a frequent crash during world unload.
- **Null-`adef` animal NPEs** — guards on `IsoAnimal.update`, `canClimbStairs`, `reattachBackToMom`, `IsoMovingObject.isPushedByForSeparate`, and `BaseVehicle.save` for animals whose definition failed to resolve (broken mod packs, missing animal types).
- **Idempotent `SpriteConfig.onAddedToOwner()`** — skips re-init if already initialized, so sync packets do not re-reset sprite state mid-game.
- **Case-insensitive whisper** — `ChatServer.processWhisperMessage` matches usernames case-insensitively and resolves to the canonical username (vanilla silently drops whispers when capitalization differs).
- **Failed workshop downloads are diagnosed and retried instead of crashing with no explanation** — a subscribed workshop item that Steam cannot download (hidden, unlisted, or removed item, or the temporary "Failed to get manifest request code, 'Access Denied'" window anonymous game-server logins hit right after an item updates) crashes vanilla with an NPE: the install-fail branch calls `ZomboidFileSystem.deleteDirectory(GetItemInstallFolder(id))` and `GetItemInstallFolder` returns null when the item was never installed. Storm null-guards `deleteDirectory`, then on install failure asks Steam's anonymous Web API (one batched `GetPublishedFileDetails` call) for each missing item's status and logs a per-item verdict (`StormWorkshopItemProbe`), retries the install 3 times 20 s apart to ride out the transient post-update deny-window, and if it still fails prints a banner with each item's ID, title, page URL, diagnosis, and remediation before letting startup fail (`StormWorkshopInstallRecovery`). The server never starts without its configured workshop items, matching vanilla — the difference is the log now tells you which item is failing and what Steam says about it.
- **Translator "Missing translation" spam** — `Translator.getText` short-circuits when the input doesn't look like a translation key, so already-translated UI strings do not emit false-positive warnings.
- **Admin brush-tool tiles vanish on chunk reload** — vanilla `ISBrushToolTileCursor:create()` runs entirely on the placing client and `placeMoveableInternal` never transmits generic tile objects to the server (only floor tiles and wall overlays have an `isClient()` transmit branch), so admin-placed tiles exist only in the client's local chunk copy and disappear when the area unloads and reloads. `server/StormBrushToolFix.lua` routes the placement through `sendClientCommand`; the server (gated on `Capability.UseBrushToolManager`) re-runs the vanilla create logic, which transmits the object to all clients and persists it in the server's chunk save.

## Mod-loader extensions

- **Mod jars on the classpath** — every `.jar` inside a mod's version-specific directory (e.g. `42/`) is loaded into `StormClassLoader` and scanned for a `ZomboidMod` entry point.
- **Lua auto-injection from jars** — any `lua/` directory inside a mod jar is registered into the game's Lua environment on `OnZomboidGlobalsLoad`, so a Storm mod ships its client/server/shared Lua next to its Java code in the same jar.
- **Annotation-driven HTTP / event / command surfaces** — mods register HTTP endpoints (`@HttpEndpoint`), event handlers (`@SubscribeEvent`), client-command handlers (`@OnClientCommand`), and server console commands (`StormCommandRegistry.MOD_COMMANDS`) without touching vanilla wiring.
- **`io.pzstorm.storm.halo.StormHalo`** — Java API to draw a temporary speech bubble over a player's head from server-side mod code (`setHalo(target, text)`, `setHalo(target, text, r, g, b)`, `setHaloFor(viewer, target, text)`). Backed by `client/StormHalo.lua` and PZ's native `IsoGameCharacter:addLineChatElement`, so bubbles render over remote players with no chat-log entry.
- **`PersistedBooleanConfigOption`** — subclass of vanilla `BooleanConfigOption` that auto-persists its value to `~/Zomboid/Storm/persisted-map-config-options/<name>.json` and reloads on construction. Drop-in replacement for mods that need a per-server toggle.
- **`StormUtils.getTextureResourceFromStream(name, classLoader)`** — load a PZ `Texture` straight from a jar resource without staging it on disk first.
- **`StormPrometheus.registry()`** — shared `PrometheusRegistry` for mod metrics; instruments registered here are scraped at `/metrics` alongside Storm's own (see [Prometheus Metrics](metrics.md) for naming conventions).
- **FMOD JNA bindings** — `io.pzstorm.storm.jna.fmod.FmodJNA` exposes the running game's FMOD system handle, 3D listener / channel attributes, cone settings, and custom roll-off curves via JNA, so mods can drive native audio without re-binding the library or shipping their own copy.
- **LuaLS type-stub dump** — every Java class exposed to Lua is written out as a LuaLS-compatible stub under `lua_stubs/` so IDEs can lint Lua against the live game API.

## Lua shipped to connected clients

Storm is a server-side framework and does not install onto player game clients.
A handful of player-facing conveniences are implemented as Lua files that ship
inside Storm's jar under `media/lua/client/`; they reach connected players
through the vanilla mod-distribution flow and talk back to the server over
`sendClientCommand` — no client-side Storm Java, no client launch-option
changes.

- **Low-RAM detection popup** — `client/StormRamAllocation.lua` reads the joining player's `-Xmx` value, reports it to the server (populating `GET /storm/ram-allocations`), and pops up a "your game has <4 GiB allocated, consider `-Xmx8g --`" warning with a "don't show again" tickbox (persisted to `StormRamAllocationSettings.txt`). If a player with ≤ 3221 MB allocated complains about lag in chat ("lag", "stutter", "freezing", "fps", …), the server detects it via a server-side patch on `ChatServer.sendMessage` (dispatching `OnServerChatMessageEvent`), broadcasts a reminder to server chat, and re-opens the popup on that player's screen (at most once per 5 minutes per player).
- **Admin-requested screenshots** — `/screenshot <username>` (see [Built-in Server Commands](mod-author-guide.md#built-in-server-commands)) tells the named player's game client to render a screenshot via `Core.takeScreenshot`, base64-chunk it, and stream it back to the server, which writes it to the player's Lua cache dir as `storm_screenshot_<user>_<id>.png`.
- **Bootstrap verification** — `client/StormBootstrapVerification.lua` logs a one-line confirmation to the connected player's log that Storm-shipped Lua loaded, so a misconfigured server is visible from the player's console without enabling debug logging.
